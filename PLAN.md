# lockem — виртуальное скрытие приложений по комбо (Magisk-модуль)

> ⚠️ **Этот документ не вполне актуален.** Это исходный проектный план из сессии планирования. Часть
> деталей с тех пор уточнилась в коде и в `HANDOFF.md` — при расхождениях источник истины: сначала код,
> затем `HANDOFF.md`, и только потом этот план. Держим его для контекста и обоснований решений («почему»).

## Context

Нужен Magisk-модуль для **личного Pixel 9a (Android 16)**, который по заданной
комбинации аппаратных кнопок (power/volume) **обратимо прячет** выбранные приложения
(disable + hide), а по обратной комбо — возвращает их. Это приватность/анти-подглядывание
на собственном рутованном устройстве; никакого удаления данных и хука входа — только
обратимое скрытие штатными средствами Android (`pm disable-user`, `pm hide`/`unhide`,
`pm enable`).

Окружение подтверждено пользователем:
- Root: **Magisk Alpha**, уже стоит **TrickyStore** и используется **KsuWebUI** (standalone-рендерер
  module WebUI) — его и переиспользуем для настройки. `ksu.exec(cmd)` даёт синхронный root-shell из JS.
- Объём: **всё сразу** (ядро + все опции-чекбоксы) в v1.
- Сборка нативного демона: решение за мной → **Android NDK standalone (ndk-build), ABI arm64-v8a**.

Директория проекта пустая (greenfield), git не инициализирован. Разработка идёт на Windows 11;
компиляция — NDK под Windows, выкладка на устройство — через KsuWebUI/adb.

**Тестирование — двумя треками:** сначала на **рутованной виртуалке** (сейчас создаётся) — там
проверяем всю функциональную логику; на **реальном Pixel 9a** — потом, для пунктов, которым виртуалка
не доверяет (см. раздел Verification). ⚠️ **Главная оговорка по VM:** образы эмулятора/GSI часто идут в
**SELinux permissive** — тогда AVC-денайлы НЕ всплывут на VM, но всплывут на телефоне (enforcing). То
есть VM отлично проверяет pm/hide/действия/WebUI/матчер, но **sepolicy и доступ демона к evdev
надо перепроверить на телефоне.**

| Конфиг-файл в ФС, сигнал демону | ✅ реализуемо | Флаг-файлы + inotify / SIGHUP. Надёжнее сокета для моста из WebUI. |

**Итог:** схема реализуема целиком. Ядро (комбо → disable+hide/unhide+enable, запись комбо, WebUI,

фоллбэки: **recents-эскизы, lockdown-биометрия, Private Space stop-user**.

## Архитектура

Три части, чувствительное — только в UI-конфиге; демон (который реально прячет) — снаружи любого профиля.

1. **`lockemd`** — нативный C-демон (aarch64), `late_start` из `service.sh`. Читает evdev **пассивно**
   (в быту без grab; uinput нет; EVIOCGRAB только на окно записи), матчит паттерны-рецепты, выполняет
   lock/unlock, авто-lock, запись комбо.
   Невидим как процесс (нет иконки, нет записи в accessibility).
2. **Конфиг + состояние** — в `/data/adb/lockem/` (вне каталога модуля, чтобы переживать обновление
   модуля): `config.json` (пакеты, два паттерна, флаги опций), `state.json` (сохранённые прежние значения
   для восстановления), флаг-файлы управления, лог.
3. **WebUI** — `webroot/` модуля, раздаётся KsuWebUI (менеджер и так под скрытием). Пишет `config.json`,
   сигналит демону через флаг-файлы (`ksu.exec`), запускает режим записи комбо.

Поток управления WebUI→демон: WebUI через `ksu.exec` трогает флаг-файлы в `/data/adb/lockem/`
(`reload`, `record_lock`, `record_unlock`); демон следит через inotify, перечитывает конфиг / входит в
режим записи и возвращает результат в файл, который WebUI поллит.

**Кроссплатформенность (принцип).** Где можно — делаем переносимо между рут-решениями:
- Стандартный **формат Magisk-модуля** (`module.prop`, `service.sh`, `sepolicy.rule`, `webroot/`) —
  исполняется на Magisk, KernelSU и APatch без изменений.
- WebUI-мост с **автодетектом**: `ksu.exec` (KsuWebUI/standalone), официальная `kernelsu` JS-lib, MMRL —
  тонкая обёртка `exec()`, которая выбирает доступный интерфейс.
- Демон — **чистый C**, без привязки к конкретному менеджеру; все действия через штатные `pm`/`cmd`/`am`.
- Конфиг (`config.json`) и CLI `lockem` работают **headless** — GUI не обязателен (важно для
  восстановления, когда менеджер скрыт).
- `sepolicy.rule` — общий; доводится по реальным AVC на телефоне.

Конфиг намеренно **не** в каталоге модуля (обновление модуля затирает его), а в `/data/adb/lockem/`.
`customize.sh` создаёт этот каталог при первой установке и не трогает существующий конфиг при апдейте.

### CLI `lockem` (`/system/bin/lockem`)

Маленькая root-утилита на PATH любого root-шелла. Подкоманды:
- `lockem lock` / `unlock` — применить / снять скрытие по всем пакетам из конфига;
- `lockem reload` — сигнал демону перечитать конфиг;
- `lockem status` — что сейчас спрятано, жив ли демон;
- `lockem record-lock-combo` / `record-unlock-combo` — запустить режим записи соответствующего комбо.

**Ключевое:** `unlock` **самодостаточен и не зависит от живого демона** — читает список пакетов из
`/data/adb/lockem/` и сам гоняет `pm unhide`/`pm enable`. Поэтому он работает как восстановление из
adb-su / recovery / GSI, и им же пользуется boot-escape. Пишется как POSIX-shell (переносимо, идёт даже в
recovery). `lock`/`reload`/`record-*` предпочтительно идут через демон (флаг-файлы), но `unlock`
всегда может всё вернуть в одиночку.

## Поведение lock / unlock (точные последовательности)

На каждом выбранном пакете (`cmd package`/`pm` из root-демона):

- **lock** (именно в этом порядке):
  1. **disable-ось** (настраивается флагом `strict_disable`):
     - по умолчанию: `pm disable-user --user 0 <pkg>`;
     - `strict_disable=true`: сначала `pm disable <pkg>` (из root может пройти), при ошибке
       (`Shell cannot change component state` и т.п.) — фоллбэк на `pm disable-user --user 0 <pkg>`.
  2. `pm hide <pkg>` — основная ось «не существует для юзера» (на A16 — проверить видимость в Settings).
  3. `am force-stop <pkg>` — попутно убирает карточку из recents (ядро чистки recents, см. ниже).
- **unlock** (обратный порядок — пока пакет hidden, часть операций видит его как «не установлен»):
  1. `pm unhide <pkg>`
  2. `pm enable <pkg>` (возвращает в enabled независимо от того, был disable или disable-user).

> Почему hide — главная ось: именно `hide` убирает пакет из виду юзера; `disable` — вторичная ось
> «не запускается». `enable` reverse'ит обе в *enabled* (не в прежний DISABLED_USER). App'ы —
> device/profile-owner отключить нельзя ни одним способом.

**Про «выключил через adb `disable` → включится ли через adb `enable`?»** `pm enable` разрешён даже
не-root adb-шеллу (uid 2000 может ставить enabled/default/disabled-user), так что `enable` снимает
`disable`. Подвохи: (а) сам `pm disable` обычного app из не-root шелла **запрещён** — выключить можно
только из root; (б) если app ещё и `pm hide`-нут, пока он hidden `enable` его «не видит» — сначала
`pm unhide`, а **unhide требует root**. Итог: из голого adb (без рута) hidden-app не вернуть; из root
(su / adb-root / наш CLI) `unhide` + `enable` возвращают всё.

Прерывание ровно между двумя вызовами (kill демона / ребут в середине батча) оставит пакет в
промежуточном состоянии — не ломается, на следующем заходе снимаем оба флага (демон при старте
нормализует состояние по `config.json` + `state.json`).

**Чистка recents — всегда (ядро, не опция):** это **side-effect от `am force-stop`** (который и так в
lock-последовательности) — он убирает карточку из recents, снимает уведомления, гасит фоновую работу, но
**данные не трогает** (force-stop ≠ clear-data; app стартует с нуля при следующем запуске). Плюс
best-effort попытка удалить таск (метод подобрать на A16; нет метода — пропускаем, вреда ноль). Историю
уведомлений — туда же подстраховкой.

**Защитный блок-лист (обязателен).** Демон отказывается лочить критичные пакеты (активный launcher,
`com.android.systemui`, `android`, пакеты рут-менеджера, от которых зависит выдача su) — чтобы
force-stop/hide не дестабилизировал систему. В WebUI такие пакеты либо скрыты из списка, либо помечены
«нельзя».

## Конфигурация комбинаций

Демон работает **пассивно**: читает поток событий `/dev/input/eventN` и ищет совпадение с паттерном
(постоянного EVIOCGRAB и uinput нет — см. ниже). Паттерн — это **упорядоченный рецепт токенов** (ровно в
том виде, в каком показываем пользователю и в каком он его повторяет):
- **нет параллельных нажатий** → последовательность из **click(K)** и **hold(K)** (hold = удержание
  ≥ порога ~500 мс, настраивается). Пример: `Vol+ click, Vol+ click, Vol- hold`.
- **есть параллельные** (одна клавиша зажата, пока актуируется другая) → явные **press(K)** и
  **unpress(K)** вокруг вложенных действий. Пример: `Vol+ press, Vol- click, Vol+ unpress` = «зажать
  Vol+, при нём кликнуть Vol-, отпустить Vol+». Это и поднимает энтропию.

**Запись:** на время окна записи демон берёт **временный EVIOCGRAB** на power/volume-ноды (короткий
захват, НЕ постоянный) — чтобы телефон не реагировал на нажатия при наборе (не гаснет, не показывает
power-menu). Тач-экран grab'ом не затронут → кнопку «Готово» в WebUI жмёшь спокойно. Демон ловит сырые
события, нормализует в рецепт токенов, **сразу отпускает grab** (также по таймауту; при падении kernel
снимает grab на закрытии fd), сохраняет в конфиг; WebUI показывает рецепт человекочитаемо — «в каком
порядке накликать».
Альтернатива без физического ввода (grab-free): **ручной конструктор рецепта в UI** — выбрать клавиши и
токены из списков, ничего не нажимая. Делаем обе.
**Срабатывание (повседневное):** полностью **пассивно** — слушаем живой поток, grab НЕ берём.

**uinput НЕ используем нигде; постоянный grab НЕ используем** — grab только на короткое окно записи.
В быту слушаем пассивно и реагируем постфактум; допускаем, что система попутно отреагирует на комбо
(громкость, power-menu и т.п.) — это ок, лишь бы плагин поймал паттерн. Единственная реально вредная
оговорка: `power+vol-down` = **скриншот** (осядет в галерее → демаскирует) — в WebUI предупреждаем и не
советуем вешать на него. 5× power = SOS, долгий power = power-menu — тоже предупреждаем, безвредный шум.

дестабилизировать систему. Для обычных прикладных app — ок; в UI предупреждаем и дефолтим на `disable-user`.

## SELinux

Процессы из magiskd живут в `u:r:magisk:s0` (фактически permissive), поэтому демон из `service.sh`
скорее всего откроет `/dev/input/eventX` на чтение сразу (uinput не нужен — grab не используем). На случай
денайлов — `sepolicy.rule` (применяется до init). Методика: собрать `dmesg | grep 'avc: denied'`,
дописать точные `allow`-правила под реальные типы/классы (`input_device`/`chr_file`), итерировать.
Типы не угадываем — берём из денайлов.

  случае, так что собрать можно и вручную одной командой.

## Восстановление владельца и модель угроз

**Фундаментальная правда (читать первой).** Любой путь восстановления, доступный владельцу, = путь
отката, доступный тому, у кого телефон в руках. Причина: (1) загрузчик разблокирован (иначе рута нет),
(2) комбо хранится в `/data/adb/lockem/config.json` **в открытом виде** (по решению — не шифруем),
(3) шифрования-при-хранении против рута нет. Поэтому **lockem — сокрытие/обфускация, а не криптозамок**:
держит против взгляда через плечо, случайного человека со схваченным разблокированным телефоном, беглого
осмотра UI. **Не держит** против форензики / грамотного оппонента с устройством — тот загрузит рут через
fastboot и прочитает плейнтекст-комбо либо просто снимет hide/disable (скрытые пакеты перечислимы:
`pm list packages -d`/`-a`, `dumpsys package` → `hidden=true`; точные флаги на A16 проверить). Нельзя
одновременно «владелец всегда восстановит» и «рут-оппонент не откатит», пока секрет в плейнтексте и
загрузчик открыт. Это ограничение фиксируем в README явно.

**Варианты восстановления:**
- **Обратная комбо** — штатный путь, без UI (демон жив, рут выдан ему при boot).
- **Boot-combo escape — ЕДИНСТВЕННЫЙ фоллбэк, который мы строим.** Проверяется **демоном при его старте**
  (`late_start`, т.е. после первой разблокировки lock-скрина — раньше `/data` не смонтирована, BFU).
  Сценарий: ребут → разблокировать lock-скрин своим PIN → в окне старта демона (первые ~N сек) держать
  **Vol+** → демон читает текущее состояние клавиш (`EVIOCGKEY`) + слушает окно и делает `unlock`.
  Без adb/UI, всегда включён, неотключаем. **Конфликта с bootloader/recovery нет:** те входят по
  Power+Vol-Down из выключенного состояния и обрабатываются прошивкой ДО старта Android/демона; наш
  escape — на Vol+ и уже внутри системы. (Какие клавиши прошивка Pixel 9a грабит на раннем boot —
  проверить на устройстве.) Если демон вообще не стартует — остаётся CLI из recovery, ниже.
- **Ключевой момент: `unlock` делает сам демон, а он жив и рутован независимо от того, что Magisk-app
  отключён** (рут выдан ему magiskd при boot, UI не нужен). `unlock` возвращает ВСЕ залоченные пакеты,
  включая **сам Magisk-app и KsuWebUI** → **UI возвращается**. Поэтому в норме внешних инструментов не
  надо: хватает boot-escape (или pre-authorized `adb shell su -c 'lockem unlock'`, если su для ADB
  заранее выдан и adb включён).
- **Крайний случай — демон вообще не стартует.** Тогда нужен внешний рут над `/data`: загрузить
  **root-способную среду** (userdebug-GSI / recovery с adb-root) через `fastboot boot <img>` — **не тот же
  запатченный init_boot** (он даст ровно то же состояние и не поможет) — и там прочитать плейнтекст-комбо
  из `config.json`, либо запустить `lockem unlock`, либо снести модуль. Конкретный образ/метод под
  Pixel 9a (TWRP может не быть) — **продумать и зафиксировать в README позже, сейчас не реализуем.**

⚠️ **Ребут нейтрален:** `service.sh` lock НЕ переприменяет (не ломаем загрузку), а app остаются спрятаны
сами (флаги персистентны). Значит ребут ничего не «чинит» и не ломает; разлочка — обратной комбо в
системе либо boot-combo escape при удержании клавиши. Опция теперь гасит Dev Options, а **не adb**, так
что adb-сеть восстановления не рвётся.

**Сокрытие менеджера Magisk / KsuWebUI.** magiskd продолжает выдавать рут уже выданным (lockem,
pre-granted ADB) по сохранённой политике — сам lockem не отвалится. Но **новый интерактивный su-запрос**
не покажет окно подтверждения (Activity менеджера отключена) → таймаут → deny. KsuWebUI живёт внутри
менеджера → его сокрытие убивает GUI-конфиг до unlock (остаётся CLI). **Рекомендация:** менеджер прятать
штатным **Magisk hide (repackage, случайное имя/иконка)** — прячет, не ломая выдачу su; прикладные таргеты
прятать lockem-ом; менеджер/KsuWebUI — опционально, осознавая переход на headless-конфиг.

## Анти-кирпич / безопасность

- **Резерв `init_boot`** (общая Magisk-гигиена на Pixel — Magisk шьётся в init_boot): сделать бэкап образа
  до экспериментов. Сам модуль boot не трогает.
- **Эскейп Magisk:** при проблемах модуль отключается `touch /data/adb/modules/lockem/disable` (или
  удалением каталога) из adb/recovery; при disable демон не стартует.
- **Фейл-сейф демона:** при невалидном/пустом конфиге — ничего не делает. В быту grab не держится вообще
  (чисто пассив); если демон упадёт во время окна записи — fd закрывается → kernel снимает временный grab
  → кнопки восстанавливаются сами.
- **`uninstall.sh` — полный откат:** `unhide` + `enable` для **всех** пакетов из конфига, восстановление
  `settings` из `state.json`, остановка демона. Так удаление модуля гарантированно возвращает телефон в
  норму, даже если он был «в locked».
- Все деструктивно-необратимого нет (ни удаления данных, ни хука входа) — по условиям.

## Шаги реализации (после одобрения)

1. **Скелет модуля:** `module.prop`, `customize.sh`, `service.sh`, `post-fs-data.sh`, `uninstall.sh`,
   `sepolicy.rule` (первая версия), раскладка каталогов, `/data/adb/lockem/` + дефолтный `config.json`.
2. **Нативный демон — ввод:** `input.c` — перечисление устройств по capability, пассивный цикл чтения
   (epoll) событий. Без uinput; EVIOCGRAB только на окно записи (временно). Отдельно проверить чтение при
   выключенном экране.
3. **Матчер паттернов:** `pattern.c` — рецепт токенов (click/hold и press/unpress для параллельных);
   матч против живого потока; режим записи (временный grab-окно) → нормализация в рецепт + сохранение;
   ручной конструктор рецепта (grab-free) на стороне WebUI.
4. **Действия:** `actions.c` — lock/unlock-последовательности, force-stop/recents, вибро (с фоллбэками),
   Private Space, lockdown (с фоллбэком), dev-options, сохранение/восстановление через `state.json`.
5. **Авто-lock + boot-escape:** **boot-combo escape** — демон при старте короткое окно слушает
   клавишу-эскейп (Vol+) и при удержании делает `unlock`; авто-lock по screen-off и таймауту (детект
   экрана — подобрать метод). **Переприменения lock при ребуте НЕТ** (загрузку не трогаем).
6. **CLI `lockem`:** `system/bin/lockem` (POSIX-shell) с подкомандами `lock`/`unlock`/`reload`/
   `status`/`record-lock-combo`/`record-unlock-combo`. `unlock` — **самодостаточный** (без демона, прямые `pm`),
   для headless-восстановления из adb-su/recovery/GSI и для boot-escape; остальные — через демон.
7. **Control-loop:** inotify на флаг-файлы (`reload`/`record_lock`/`record_unlock`), SIGHUP-reload.
8. **WebUI:** `index.html`/`app.js`/`style.css` — список пакетов (из `pm list packages`), запись двух
   комбо (кнопка → ставит флаг → поллит результат), чекбоксы опций, предупреждение про `power+vol-down`
   и про «отключение Dev Options». Ручной конструктор рецепта (grab-free). Мост `exec()` с автодетектом
   (`ksu.exec`/`kernelsu`/MMRL).
9. **Сборка:** `build.sh` + `jni/Android.mk`/`Application.mk`; собрать `bin/lockemd` (или выдать команды).
10. **Упаковка:** zip модуля, `README.md` с установкой/откатом/device-чеклистом и **явной моделью угроз**.

- [ ] Boot-escape: какие клавиши прошивка Pixel 9a грабит на раннем boot; длина окна старта демона, в

- [ ] Путь вибро: `cmd vibrator_manager` / `cmd vibrator` / sysfs — что доступно на ядре Pixel 9a.
- [ ] Чистка recents: убирает ли `am force-stop` карточку скрываемого app; есть ли рабочий способ удалить

- [ ] Lockdown: есть ли рабочий shell-триггер strong-auth; иначе фиксируем фоллбэк «залочить экран».
- [ ] SELinux: собрать `avc: denied` для чтения `/dev/input/*`, при необходимости дописать `sepolicy.rule`.

## Verification (как убедимся, что работает end-to-end)

### Track A — рутованная виртуалка (сейчас)
Что VM проверяет надёжно: pm hide/unhide/disable/enable, lock/unlock-последовательности, конфиг,
WebUI (если в VM есть рендерер) или config-файл + режим записи (включая временный grab), матчер
паттернов-рецептов, force-stop/recents, Private Space, авто-lock по screen-off/таймауту,
`uninstall.sh`-откат. Проверить также, что power/volume приходят как evdev-события (`getevent -lp`) и
читаются пассивно.
**Чему VM НЕ доверяем:** см. ⚠️ в Context — если VM в permissive, sepolicy и реальные денайлы доступа
к evdev там не видны; вибро/биометрия-lockdown физического эффекта не дадут.

Функциональный прогон (на VM, потом повторить на телефоне):

1. Установить zip через Magisk Alpha (или рут-менеджер VM), ребутнуть. Проверить, что `lockemd` поднялся (`ps -A | grep lockemd`,
   лог в `/data/adb/lockem/lockem.log`), и что обычные power/volume работают как раньше (grab в быту не держим).
2. В WebUI (KsuWebUI) выбрать 1–2 тестовых пакета, записать lock- и unlock-комбо.
3. Набрать lock-комбо → целевые app исчезают из drawer и (проверить) из Settings→Apps; карточки из recents
   ушли; вибро/опции отработали. Набрать unlock-комбо → всё вернулось.
4. Ребут в locked-состоянии → app остаются спрятаны **сами** (флаги персистентны); `service.sh` lock не
   переприменяет, только стартует демон. Отдельно: удержание Vol+ при загрузке → всё разлочилось (escape).
5. Откат: удалить модуль → `uninstall.sh` возвращает все пакеты (enable+unhide) и settings; телефон в норме.
6. Фейл-сейф: `kill lockemd` в locked-состоянии → кнопки продолжают работать (в быту grab не держался), app
   можно вернуть переустановкой/`pm enable`.

### Track B — реальный Pixel 9a (потом)
Повторить прогон 1–6 на enforcing-телефоне и дополнительно закрыть то, чему VM не доверяет:
- SELinux: собрать реальные `avc: denied` для чтения `/dev/input/*` (и ioctl EVIOCGRAB при записи),
